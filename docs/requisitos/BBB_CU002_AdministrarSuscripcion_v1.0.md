# CU-002 · Administrar la suscripción y su vigencia

Formato CU-01 (MD Anexo D) · Versión 1.0 · 18/10/2026 · Autor: Raúl Treviño Licona · Estado: propuesto

| Campo | Contenido |
|---|---|
| ID y nombre (1) | CU-002 Administrar la suscripción y su vigencia |
| Objetivo (2) | Mantener la suscripción vigente con el plan adecuado, avisar antes del vencimiento y restringir la operación cuando no se renueva. |
| Actores (3) | Principales: administrador institucional y superadmin. Secundario: sistema (tareas programadas y correo). |
| Disparador (4) | D1. El administrador institucional abre "Suscripción". D2. El superadmin abre "Instituciones". D3. El programador de tareas ejecuta `spei:alertar-vencimientos` (diario a las 07:00) y `spei:aplicar-vencimientos` (diario a las 00:05). |
| Precondiciones (5) | P1. La institución existe. P2. El actor tiene sesión y el rol indicado. |
| Postcondiciones (6) | Q1. Plan, límites, fecha de corte y estado actualizados según la acción. Q2. Cada cambio queda en `logs_auditoria` (`CAMBIAR_PLAN`, `RENOVAR`, `CAMBIAR_ESTADO`). Q3. Las alertas quedan en `notificaciones` y en la cola de correo. |
| Flujo principal (7) | **Consultar (RF-004):** 1. El sistema muestra plan, límites con su uso actual, fecha de inicio, fecha de corte, días restantes y estado. **Cambiar plan (RF-003):** 2. El administrador institucional (o el superadmin) elige otro plan activo. 3. El sistema verifica que las áreas y los recursos actuales no superen los nuevos límites. 4. Actualiza plan y límites y audita. **Renovar (RF-004):** 5. El superadmin registra la renovación. 6. El sistema calcula la nueva fecha de corte como el mayor entre la fecha de corte y hoy, más `duracion_dias`, y si estaba en `solo_lectura` la regresa a `activa`. **Alertar (RF-005):** 7. A 7, 3 y 1 días del corte, el sistema crea una notificación `ambas` para cada administrador institucional activo y encola el correo. **Vencer (RF-006):** 8. Si `fecha_corte` es anterior a hoy y el estado es `activa`, la institución pasa a `solo_lectura` (RN-013) y se audita con usuario nulo (sistema). |
| Flujos alternos (8) | A1. El superadmin cambia el estado manualmente según MBD Tabla 28: `activa` → `solo_lectura`, `suspendida` o `cancelada`; `solo_lectura` → `activa` o `cancelada`; `suspendida` → `activa` o `cancelada`; `cancelada` es final. A2. Si ya existe la alerta del día para ese administrador, no se duplica. |
| Excepciones (9) | E1. Nuevos límites menores al uso → "El plan no admite las áreas o recursos ya registrados." E2. Transición no permitida → "No se permite el cambio de estado solicitado." E3. Con la suscripción en `solo_lectura`, toda petición de escritura de usuarios del tenant responde 403 "La suscripción está en modo solo lectura." (RN-011), salvo cerrar sesión. E4. Con `suspendida` o `cancelada` no se permite iniciar sesión y las sesiones activas se cierran. |
| Reglas relacionadas (10) | RN-010, RN-011, RN-013. |
| Requisitos relacionados (11) | RF-003, RF-004, RF-005, RF-006, RNF-005, RNF-006, RS-006; DT-024. |
| Criterios de aceptación (12) | CA1. No se puede bajar a un plan con límites menores al uso actual. CA2. La renovación extiende la fecha de corte exactamente `duracion_dias` y reactiva una institución en `solo_lectura`. CA3. El comando de alertas genera una notificación por administrador a 7, 3 y 1 días y ninguna duplicada si se ejecuta dos veces el mismo día. CA4. El comando de vencimientos pasa a `solo_lectura` solo las instituciones `activa` vencidas. CA5. En `solo_lectura`, un POST de alta de área responde 403 y un GET del inventario responde 200. CA6. Un usuario de una institución `suspendida` no puede iniciar sesión. CA7. Solo el superadmin renueva o cambia el estado; el administrador institucional recibe 403. |
